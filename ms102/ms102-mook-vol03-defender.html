PART 01Defender XDR の全体像

守る相手は、
1製品に1つ。

XDR は、端末・メール・ID・クラウド アプリで別々に起きた検出を、1つの攻撃として結びつけて見せる仕組みです。窓口は security.microsoft.com ひとつ。まず4つの Defender が何を守るのかを、一言で言えるようにしましょう。

押さえどころ
  • Defender for Identity と Entra ID Protection は別物。前者はオンプレミス AD への攻撃を DC のセンサーで検知、後者はクラウドのサインインのリスクを判定。
  • Defender for Office 365 だけを任せたい担当者には、Defender XDR 統合 RBAC で範囲を絞ったカスタム ロール。全体管理者やセキュリティ管理者は広すぎる。
  • Defender for Identity をスタンドアロン センサーで使うなら、先にポート ミラーリングを構成する。
ここが出る！
端末をマルウェアから一元的に守りたい
Defender for Endpoint
サーバーの system ログを集めて分析したい
Log Analytics ワークスペースとエージェントの両方（Intune は別物）

PART 02インシデント対応と自動化

アラートは点、
インシデントは線。

アラートは個々の検出、インシデントは関連するアラートを束ねた「攻撃1件」です。調査が終わったら分類を付けて閉じます。修復をどこまで自動でやるかは、デバイス グループごとの自動化レベルで決めます。

押さえどころ
  • 分類は真陽性・情報提供（予期されたアクティビティ）・偽陽性の3系統。分類は検出精度へのフィードバックで、隔離したファイルは戻らない。
  • 自動攻撃中断は、確度の高いシグナルが揃うと調査の完了を待たずにデバイスの封じ込めやユーザーの無効化を行う。ランサムウェアや AiTM 攻撃で働く。
  • デバイス グループはランク順に評価され、最初に一致したグループの設定が使われる。
ここが出る！
自動修復でファイルが隔離された。元に戻したい
アクション センターの履歴から元に戻す
一部のサーバーだけ自動修復を止めたい
そのサーバーのデバイス グループを作り、自動化レベルを下げる

PART 03高度なハンティング

探したクエリは、
保存すれば見張り番。

高度なハンティングは、アラートになっていない事象まで KQL で掘り起こす機能です。対象は既定で直近30日。作ったクエリをカスタム検出ルールとして保存すると、定期的に実行してアラートを上げ続けてくれます。

押さえどころ
  • 過去を探すのは高度なハンティング、これからも見張るのはカスタム検出ルール。「クエリを実行するだけ」の選択肢は要件を満たさない。
  • カスタム検出ルールには、デバイスの分離・ファイルの隔離・ユーザーの無効化などの応答アクションを組み込める。
  • テーブル名の頭の語で、どの製品のデータかが分かる（図3-2）。URL のクリックは UrlClickEvents。

PART 04露出管理と脅威インテリジェンス

上げたいスコア、
下げたいスコア。

露出管理は「今どれだけ攻撃されやすいか」を測り、直す順番を決める場所です。似た名前のスコアが3つあり、1つだけ向きが逆になっています。話題の攻撃に自社がどこまで備えているかは、脅威分析で確かめます。

押さえどころ
  • セキュア スコアの推奨アクションは、「リスクの受け入れ」「サードパーティで解決済み」とマークできる。近い規模・業種の組織と比較もできる。
  • 攻撃パスは資産どうしのつながりを図にしたもの。多くの経路が通るチョーク ポイントから塞ぐ。
  • 脅威分析は研究者のレポートと自組織への影響、Defender TI は IP・ドメイン・ハッシュを起点にした外部インフラの調査。

PART 05EOP と Defender for Office 365

1階は標準装備、
2階から上は Defender。

すべての Exchange Online には EOP が付いてきます。その上に Defender for Office 365 Plan 1、さらに Plan 2 が乗ります。上の階は下の階の機能もすべて使えます。「その機能は何階か」を当てる問題が定番です。

押さえどころ
  • SharePoint・OneDrive・Teams を守るのは安全な添付ファイル側。メール用ポリシーではなくグローバル設定でオンにする。
  • 安全な添付ファイルは、クラウドの仮想環境で実際に開いて検査する。動的配信なら本文を先に届け、添付は検査後に届く。
  • デバイスのオンボードと Safe Documents は Defender for Endpoint 側の話。「MDO でできないことは？」の誤答に紛れ込む。

PART 06脅威ポリシーとプリセット

プリセットは、
カスタムより強い。

メールの保護設定は「プリセットに任せる」か「カスタム ポリシーを作る」かの2通りです。同じ受信者に複数のポリシーが当たると、上位の1つだけが効きます。標準プリセットはほとんどの人向け、厳格プリセットは役員や経理など狙われやすい人向けです。

押さえどころ
  • カスタムが効かないときは、その人がプリセットの対象になっていないかを疑う。効かせたい人はプリセットから除外する。
  • 送信元が p=reject を宣言したなりすましは、フィッシング対策ポリシーの「DMARC レコード ポリシーを尊重する」で拒否する（既定でオン）。
  • Defender ポータルで新しく作ったポリシーは、フィッシングの既定が検疫。既定のポリシーとは違う。
ここが出る！
役員だけ、標準より積極的に検疫したい。手間は最小で
役員を対象に厳格プリセットを有効にする
既定のポリシーで、フィッシングはどう処理される？

PART 07検疫・制限付きエンティティ・許可／ブロック

送れなくなった人は、
解除の前に調べる。

送信スパムの上限を超えたユーザーは、制限付きエンティティとしてメールの送信を止められます。多くはアカウントが侵害されて、迷惑メールの踏み台にされた結果です。送信制限は「結果」で、原因は別のところにあります。

押さえどころ
  • 検疫されたメールにユーザーが何をできるか（プレビュー・解放の要求・解放・削除）は検疫ポリシーで決める。
  • サードパーティの訓練メールや SecOps 用メールボックスは、メール フロー ルールで許可せず高度な配信で対象外にする。
  • 調査ツールは、脅威エクスプローラー（Plan 2）とリアルタイム検出（Plan 1）。配送経路の追跡は Exchange 管理センターのメッセージ トレース。

制限付きエンティティで確認 → 侵害を調べてパスワードをリセット → 解除
マルウェア判定のファイルを許可したい

PART 08攻撃シミュレーション トレーニング

引っかかった人には、
自動で補習。

PART 09Defender for Endpoint

端末は、
入れて、決めて、止める。

Defender for Endpoint は、デバイスをオンボード（登録）してから守ります。何台あるか、どの OS かで登録方法が変わり、止めたいものによって使う道具が変わります。

押さえどころ
  • データの保存地域は最初にデバイスをオンボードした時点で固定。変えるには全台をオフボードしてから再オンボードする。
  • 脆弱性の管理（MDVM）の推奨事項から、Intune のセキュリティ タスクとして修復を依頼できる。
  • 望ましくない可能性のあるアプリ（PUA）の保護は、監査モードで数週間様子を見てからブロックに切り替える。

PART 10Defender for Cloud Apps

見つける、深く見る、
その場で止める。

Defender for Cloud Apps は、SaaS の使われ方を見える化して制御する CASB です。知らないアプリを見つける機能、使っているアプリを見張る機能、ブラウザーの操作をその場で止める機能の3つに分かれます。

押さえどころ
  • 未承認アプリはセッション ポリシーでは止まらない。プロキシを通らないから。未承認タグを付けて、Defender for Endpoint のネットワーク保護で止める（反映まで最大2時間）。
  • セッション制御が効くのはブラウザーのセッションだけ。デスクトップ版やモバイル アプリはアクセス ポリシーなどで止める。
  • ファイル ポリシーを使うには、Microsoft 365 アプリ コネクタと「ファイルの監視」が必要。
ここが出る！
許可していないファイル共有サービスの利用状況を知りたい
Cloud Discovery（MDE 連携がいちばん手軽）
非管理デバイスからのダウンロードだけ禁止したい

答え合わせ。

Q1役員向けに、標準よりも積極的にメールを検疫する保護をかけたい。管理の手間を最小にするには？

正解は B。厳格プリセットは Microsoft が管理する推奨設定で、設定値を自分で維持する必要がない。A でも実現はできるが手間が増え、優先度を上げてもプリセットには勝てない。→ PART 06

Q2あるユーザーが大量の迷惑メールを外部へ送り、メールを送信できなくなった。対応の順序として最も適切なのは？

正解は C。送信制限は結果で、原因は侵害。原因を断ってから解除する。A はすぐ再発し、B は危険を広げ、D は受信側の保護で関係がない。→ PART 07

Q3過去7日間に特定の悪意ある URL をクリックしたユーザーを特定し、今後も同じ条件で自動的にアラートを上げたい。適切な手順は？

正解は D。過去の検索は高度なハンティング（UrlClickEvents）、継続的な検知はカスタム検出ルール。メッセージ トレースはクリックを扱わず、既定のアラートでは個別の URL を条件にできない。→ PART 03

Q4既定のスパム対策ポリシーだけを使っているテナントで、各判定のメールはどう処理される？

正解は A。既定では、スパム・一括メール（BCL 7 以上）・通常のフィッシングは迷惑メールへ移動、高確度フィッシングは常に検疫。D は厳格プリセットに近い。→ PART 06 図6-2

Q5会社が許可していない外部のファイル共有サービスへのアクセスを、社内の Windows 端末から止めたい。全端末は Defender for Endpoint にオンボード済み。最も適切なのは？

正解は B。未承認タグは MDE のインジケーターに同期され、ネットワーク保護で端末からのアクセスが遮断される。A と C は Entra でサインインする承認済みアプリにしか効かない。D はメール内の URL の判定で、Web アクセスは止めない。→ PART 10 図10-2
