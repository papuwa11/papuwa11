CARD 01 / 10ID モデルと同期の準備

同期を始める前に、何を整えておく？

汚れたまま、同期しない。

ユーザーはクラウド専用か、オンプレミス AD を権威とするハイブリッドのどちらかです。同期を始める前に AD のデータを IdFix で掃除し、UPN サフィックスをテナントの検証済みドメインに揃えておきます。

押さえどころ
  • 同期ユーザーの属性はオンプレミス AD 側で変える。ライセンスや使用場所などクラウド固有の属性だけはクラウドで操作する。
  • ソース アンカーの既定は ms-DS-ConsistencyGuid。フォレスト移行があっても対応関係を保てる。
  • ソフト マッチの基本はSMTP マッチング。UPN による突き合わせは SMTP がまだない場合の代替。

CARD 02 / 10Entra Connect Sync と Cloud Sync

Connect Sync と Cloud Sync、どちらを選ぶ？

頭脳がオンプレか、クラウドか。

ディレクトリ同期の実装は2つあります。Connect Sync はオンプレミスの同期サーバーに頭脳があり、Cloud Sync はクラウドに頭脳があって、オンプレミスには軽いエージェントだけを置きます。どちらを選ぶかの設問が繰り返し出ます。

押さえどころ
  • Entra Connect がオンプレミス AD を読むときのプロトコルはLDAP。クラウドへの書き込みは HTTPS。
  • Connect Sync のまま可用性を上げるなら、2台目をステージング モードで待機させる。
  • 同じフォレストで両方を併用することもできる（同じ OU をスコープしないなどの条件つき）。
ここが出る！答えを思い出してから押す

CARD 07 / 10Identity Protection

人が危ないのか、今回のサインインが怪しいのか？

ユーザー リスクはパスワード変更、
サインイン リスクは MFA。

Identity Protection は、サインインとアカウントに関するリスクを検出して自動で対処する仕組みです。リスクは2種類あり、対処が違います。実装は条件付きアクセスで行うのが現在の推奨で、全機能には Entra ID P2 が必要です。

押さえどころ
  • 危険なユーザーのレポートで管理者が「侵害を確認」すると、Microsoft の機械学習へのフィードバックになる。単なる状態変更ではない。
  • リスク ベースのポリシーで守られるのは、P2 が割り当てられたユーザーだけ。P2 は E5・EMS E5・Defender Suite・Entra Suite に含まれ、E3 は P1。
  • 中核機能は「高度な機械学習」と「リスク ベースの条件付きアクセス」。PHS や同期の機能とは別物。
ここが出る！答えを思い出してから押す

CARD 08 / 10条件付きアクセス

ポリシーが複数当たったら、どう決まる？

ブロックが勝ち、除外が勝つ。

条件付きアクセスは「もし〜ならば、〜を要求する」というルールでアクセスを制御します。対象のポリシーはすべて評価され、順番や番号はありません。新しいポリシーはレポート専用モードから始めます。Entra ID P1 が必要で、リスクを条件にするなら P2 です。

押さえどころ
  • セキュリティ既定値群と条件付きアクセスは併用できない。条件付きアクセスを使うには先に既定値群を無効にする。
  • レガシー認証のブロックは、条件のクライアント アプリで「その他のクライアント」を選んでブロックする。POP・IMAP・SMTP AUTH は MFA の抜け道になる。
  • 管理ポータルへの MFA の必須化は、条件付きアクセスがなくても強制され、緊急アクセス用アカウントも例外にならない。パスキーや証明書ベース認証を用意しておく。
ここが出る！答えを思い出してから押す
条件付きアクセスのポリシーを有効にできない。セキュリティ既定値群が有効になっている

セキュリティ既定値群を無効にする

緊急アクセス（ブレークグラス）用アカウントの扱いは

すべての条件付きアクセス ポリシーから除外する

POP や IMAP など、MFA を回避する抜け道を塞ぎたい

条件付きアクセスでレガシー認証をブロックする

Azure の管理操作だけに MFA を求めたい

クラウド アプリに Microsoft Azure Management を指定する（すべてのクラウド アプリは広すぎる）

新しいポリシーを、特定のユーザーと SaaS アプリで適用前に試したい

CARD 09 / 10MFA の実装とデバイス ID

MFA はどの方法で有効にする？ デバイスはどう登録する？

MFA は条件付きアクセスで。

MFA を有効にする方法は歴史的に3つありますが、現在の推奨は条件付きアクセスです。デバイスも Entra ID のオブジェクトで、「準拠デバイスを要求」や Intune のポリシー配布は、デバイスが3つの状態のどれかで登録されていることが前提です。

押さえどころ
  • 特定のユーザーだけ MFA を免除するなら、条件付きアクセスの除外。ユーザーごとの MFA を「無効」にする選択肢は誤り。
  • 信頼できる場所（本社の固定 IP など）からは MFA を求めない設計もできるが、場所だけを信頼する設計はゼロトラストでは弱いとされる。
  • 条件付きアクセスのユーザー操作「セキュリティ情報の登録」で、MFA の登録を信頼できる場所からだけに絞れる。
ここが出る！答えを思い出してから押す

CARD 10 / 10Application Proxy

VPN なしで、社内の Web アプリを社外から使わせるには？

コネクタが外へ出ていくから、
穴は開けない。

Application Proxy は、オンプレミスの Web アプリの手前に Entra ID の認証（条件付きアクセスや MFA を含む）をかぶせて社外へ公開する機能です。社内に置くコネクタはクラウドへ外向きにだけ接続するので、受信ポートを開ける必要がありません。

押さえどころ
  • コネクタを複数台入れてコネクタ グループを組むと、負荷分散と冗長化ができる。
  • SSO は統合 Windows 認証・ヘッダー ベース・フォーム ベースなど、アプリ側の認証方式に合わせて選ぶ。
  • Application Proxy にはEntra ID P1 以上が必要。
ここが出る！答えを思い出してから押す

Q1買収した企業の AD フォレストは、自社フォレストとの信頼関係がない。両方のユーザーを1つの Entra テナントへ同期したい。最も適した方法は？

正解は D。Cloud Sync は切断されたフォレストを、それぞれのエージェント経由で同じテナントに同期できる。A は Connect Sync がアクティブ1台しか取れないため不可、B は待機構成、C は重い前提を課す。→ CARD 02

Q2AD FS によるフェデレーション認証を使っている。Identity Protection の「漏洩した資格情報」を検出できるようにしたい。何をする？

正解は A。漏洩した資格情報の検出は、同期したハッシュと流出情報の突き合わせで成り立つ。フェデレーションのまま PHS をバックアップとして有効にできる。PTA もハッシュを同期しない。→ CARD 03

Q3条件付きアクセス ポリシーを新しく作ったが、有効にできない。テナントではセキュリティ既定値群が有効。どうする？

正解は C。セキュリティ既定値群と条件付きアクセスは排他。条件付きアクセス自体は P1 で使えるので A は不要、D は検証手段で適用にはならない。→ CARD 08

Q4新入社員が入社初日に、MFA の方法を何も登録していない状態でサインインする必要がある。管理者が発行するものは？

正解は B。TAP は強い認証手段をまだ持たない人に、期限付きのパスコードを渡して初期登録させるための機能。アプリ パスワードは古いクライアント向けで、初期登録の手段ではない。→ CARD 05

Q5Connect Sync で「Operations OU にいて、かつ ADDPilot グループのメンバー」だけを同期している。グループの絞り込みをやめて OU の全員を同期したい。意図しない変更を避けるため、最初にやることは？

正解は A。フィルターを変えると、範囲から外れたオブジェクトは削除される。途中で30分ごとの同期が走らないよう、まず止める。B は2番目、C は変更後の確認。→ CARD 04
